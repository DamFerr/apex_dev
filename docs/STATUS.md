# Apex status (handoff file, updated in every step)

## Current state (Phase 1 complete, Phase 2 data engine in progress)
- **Latest step: only the last 5 patches.** Apex now downloads, stores and shows data for the 5 newest patches only. One place defines patch order: `comparePatch` / `patchOrder` / `lastPatches` / `KEEP_PATCHES` in `services/api/src/store.ts` (numeric, `16.9` < `16.10`; values that are not `major.minor`, like the "unknown" of a game without a version, are not patches). `store.recentPatches()` is the newest 5 seen in the data and `store.latestPatch()` the first of them. `store.saveMatch` refuses a game whose patch is not among the 5 newest (known patches plus its own), and the first game of a new patch triggers `store.pruneOldPatches()`, which deletes `participants`, `bans` and `matches` of every other patch in one transaction. `pnpm api` runs the same cleanup at every start and logs it. `rank_snapshots` (LP history) and `seeds` are never touched. The collector remembers refused matches in memory so it does not download them again on the next crawl. The `Filter` type now has `patches: string[]` instead of `patch`; the API turns `patch=latest` into the newest patch, `patch=all` into the last 5, and `patch=16.x` into that one patch (no data if it was removed). `/v1/filters` lists only the kept patches, newest first. The filter bar says "Last 5 patches" and falls back to "Latest patch" if a saved patch no longer exists. 12 new unit tests (149 in the API, 43 e2e all green).
- **Previous step: LP history.** Profile has a new "LP history" tab. The backend stores a rank snapshot (`rank_snapshots` table: puuid, time, tier, division, LP, wins, losses) every time a profile lookup fetches fresh data from Riot (profile cache is 5 min), but only when something changed since the last snapshot. `GET /v1/players/:riotId/lp-history` returns them oldest first and also takes a fresh snapshot, and still answers from storage if Riot is unreachable. The tab shows current rank, highest seen, net LP and games since tracking started (or since the last season reset), a line chart that draws in (ladder points on the Y axis labelled by division) and a "Changes" list with games and LP per period, Promoted/Demoted tags and a "New season" row. Math lives in `packages/stats-core/src/ladder.ts` (`ladderPoints`, `pointsLabel`, `lpStep`, `ladderTicks`, 400 per tier, 100 per division, Master+ one ladder).
- **Previous step: Flash key setting** (Settings > Champ select, D or F, `placeFlash` in lcu-core, client-side only).
- **Earlier step: Flash key setting.** Settings > Champ select > "Flash key" (D left / F right, default F, so nothing changes for anyone). `placeFlash(pair, slot)` in `packages/lcu-core/src/spells.ts` puts Flash on the chosen slot and leaves pairs without Flash untouched. `importSpells` applies it on the client only (the backend still returns Flash second), and the champion page "Summoner spells" line shows the same order. Stored as `flashSlot` in the `apex-ui` store (no migration needed; a missing value falls back to "F"). 6 new unit tests, 1 new e2e test (40 e2e total).
- **Earlier step: timelines.** The collector now fetches the Match-v5 timeline for a deterministic share of newly stored games (`COLLECT_TIMELINES`, default 0.25; 0 = off; one extra Riot request each, so about 20% slower collection at 0.25). From it Apex stores per player the skill order, starting items (bought in the first 90 s, undone purchases removed) and all later purchases. `/v1/champions/:id/build` gained `skillOrder` (max priority + most common first 9 levels), `startItems`, `corePath` (first three finished items in order) and `timelineGames`; the champion page shows them and the old empty "Skill order" row is filled. The item set import adds "Starting items" and "Build order" blocks when available.
- **Previous step: data-based builds.** `GET /v1/champions/:id/build?role&patch&region&rank` returns the most played rune pages (grouped by primary tree + keystone + secondary tree, each slot filled with the most common choice in that group), the most played summoner spell pair and final-inventory item blocks (Boots / Core / Situational). The champion page shows it ("Recommended build"); the Draft import now writes the collected rune page, spells and an item set, falling back to class/role defaults (and saying so in the import log) when fewer than 10 games exist.

## Decisions
- Patch window: 5 newest patches by NUMERIC order of the patches present in the data (not the clock, not game end times). A game is accepted when its patch is among the 5 newest of (stored patches + its own); an unreadable patch is refused. Deleting is automatic and permanent (games, players, runes, timelines, bans); Riot has no way to get a patch's games back except collecting again, and only while they are still in players' match lists.
- The distinct patch list is cached in memory by the store (the API process is the only writer) and updated on insert and prune; `matches.patch` now has an index (`m_patch`, created automatically on existing databases).
- Thresholds were re-checked and left alone: `MIN_BUILD_GAMES` (10) and the tier-list minimum (max(50, 0.5% of the role's games)) are absolute counts and the default "Latest patch" view is unchanged. "Last 5 patches" has the same or fewer games than the old "All patches", and every number still shows its real sample size. Revisit them once you see how many games a typical patch holds on your collection speed.
- LP history: ladder points = 400 per tier + 100 per division (IV = 0 ... I = 300) + LP; Master, Grandmaster and Challenger are one ladder starting at 2800. A difference of two values is the LP change across promotions and demotions. Wins or losses going down between two snapshots means a season reset: the chart and totals restart after it and the list says "New season" instead of inventing an LP change.
- Snapshots are only taken for profile lookups (not for the 10 players of a live game), so the table stays small and every row is a player the user chose to look at.
- Timeline data lives in three new `participants` columns (`skills`, `start`, `buys`, JSON), added automatically to existing databases. Skill order = order in which Q, W, E reach rank 5; the first-9-levels line is a real sequence from games with that max order. Core path groups games by their exact first three finished items, so its sample is smaller than the other stats and says so.
- Ranks are cumulative: "Emerald+" = Emerald IV and above. Collector reads every division ladder (I-IV) of every tier. A match is filed under the tier of the seed player it was found through.
- Riot limits are per routing host. Match-v5 uses 4 clusters (europe, americas, asia, sea), ladders/league use platform hosts. The collector picks its next player from the cluster with the fewest busy workers so all four limits stay in use.
- Network errors and Riot 5xx are retried (3 and 2 times, growing pause) inside `HttpRiot`; the final message names the real cause.
- Collector status only shows an error while it is recent (3 min) or fatal (bad key).
- Tier list hides champions with too few games in a role: under max(50, 0.5% of the role's games). A champion only counts in a role when that role is >= 10% of its games.
- Champion display names come from Data Dragon on the client (`useChampName`), never the raw id.
- Rune, spell and item set import use collected games when the top rune setup has at least 10 games (`MIN_BUILD_GAMES`); otherwise class/role defaults, labelled as such in the import log. Lookup order: current filters + role, then all patches + role, then all patches + any role.
- Rune page = real data only: primary runes and shards are per-slot modes within the most played setup; the secondary pair is the most common real pair (so the page is always valid). The win rate shown is the whole setup's, never an invented combination.
- Items are FINAL inventories (what players owned at game end), not a build order; starting items and order need timelines. Boots = Data Dragon tag Boots with no upgrade; other items must cost 2000+ and have no upgrade.
- Item sets: the client replaces its whole list on write, so Apex reads the list first, keeps every set that is not titled "Apex: ..." untouched, replaces only its own set for that champion (uid `apex-<championKey>`), keeps at most 15 Apex sets, and writes nothing if the list cannot be read.
- The Rust request allowlist now also permits GET `/lol-summoner/v1/current-summoner` and GET/PUT `/lol-item-sets/v1/item-sets/<numeric id>/sets`, nothing else under those prefixes.
- `participants` has a new `perks` column (full rune page as JSON), added automatically to existing databases. Games collected before this step have no rune page and are ignored by rune stats (item and spell stats still use them).
- The overlay window code (`overlay.rs`, `Overlay.tsx`) stays as groundwork but is not reachable from the UI until it has real content.

## Known issues / limits
- The first start after this update deletes every game older than the 5 newest patches from your local database. The SQLite file does not shrink by itself (freed space is reused by new games); there is no VACUUM step yet.
- A game that was stored and then pushed out of the window by a new patch is not remembered, so it is downloaded and refused once more (about 1 request) the next time its player is crawled; after that it is skipped until the backend restarts.
- A development key caps collection at roughly 3 games/s total (100 req / 2 min per cluster). Only a production key raises it.
- A player stays filed under the tier they were first seeded at (rank changes are not re-read until the weekly ladder refresh).
- Only a share of games have timelines, and games collected before this step have none. There is no backfill yet, so skill order, starting items and build order fill in as new games arrive (a champion needs enough timeline games; every stat shows its sample size).
- LP history only knows the moments Apex looked: there is no backfill (Riot has no LP history endpoint), history for a player starts the first time Apex looks them up, and changes are totals between two checks, never per game. Apex does not look anyone up on its own, so for your own account the history fills in each time you open Home, Profile or the LP tab. Snapshots are kept per player, locally, with no limit on age (the API returns the latest 500).
- Item set import and the new Rust allowlist entries have NOT been run against a real League client yet (no client or Rust toolchain in the build environment). Test: Draft screen, Import now, then check the item sets in the client's item shop. Tier list shows an empty state until a role has enough games.
- The real League client connector (Rust) still needs testing on your machine.
